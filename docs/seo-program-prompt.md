## กฎประจำโปรเจค (ส่งพร้อมข้อความแรก และถือใช้ทุกเฟส)

1. **ไฟล์ .md คือต้นฉบับเดียวของบทความ** เขียนและแก้ที่ `content/articles/NN-slug.md` เท่านั้น
   HTML ของเว็บและ Google Doc ต้องแปลงจากไฟล์นี้ด้วยสคริปต์ ห้ามแก้ HTML หรือ Doc ตรง ๆ
   เวลาเขียนหรือแก้บทความ ต้องอัปเดตไฟล์ .md คู่กันเสมอ
2. **Google Doc ที่ส่งลูกค้าใส่เฉพาะเนื้อหาบทความ + บรรทัด "คีย์เวิร์ด:"** ไม่ใส่ SEO meta, สเปกรูป,
   ลิงก์ภายใน หรือโน้ตถึงทีม ตั้งชื่อไฟล์ `N. ชื่อเรื่อง` (เลขลำดับ จุด เว้นวรรค)
   Drive API แก้เนื้อหา Doc เดิมไม่ได้ ถ้าต้องแก้ให้ย้ายตัวเก่าลงถังขยะแล้วสร้างใหม่ และบอกฉันว่าลิงก์เปลี่ยน
   ก่อนสร้าง Doc ทุกครั้งให้ list โฟลเดอร์ก่อน เพราะฉันอาจย้ายหรือลบไฟล์ไปแล้ว
3. **Voice ของบทความ**: ผู้อ่านเป็นมืออาชีพ (ตามกลุ่มเป้าหมายข้างบน) เขียนสุภาพ เหมือนวิศวกรอาวุโสเขียนให้เพื่อนร่วมวงการ
   ไม่เรียกผู้อ่านว่า "คุณ" ห้ามใช้ขีดยาว (— และ –) ในเนื้อความ (en dash ใช้ได้เฉพาะช่วงตัวเลข เช่น 23–25)
   ห้ามสำนวน AI ภาษาไทย (ในโลกปัจจุบัน, ไม่เพียงแต่…แต่ยัง, นอกจากนี้, สรุปได้ว่า, ตอบโจทย์, ครบวงจร, มาดูกัน,
   เมื่อพูดถึง, ถือเป็น/นับเป็น, ทีนี้, เป๊ะ, ง่าย ๆ คือ, จะเห็นว่า, นี่คือเหตุผล, โครง "ไม่ใช่ X แต่เป็น Y", ยกของมาสามอย่างเสมอ)
   หัวข้อเป็นประโยคบอกเล่า ยกเว้นส่วนคำถามที่พบบ่อย ย่อหน้าแรกตอบคำถามของหัวข้อจบใน 40–60 คำ
   ทุกย่อหน้ามีตัวเลขหรือชื่อมาตรฐาน ปิดบทด้วยหัวข้อ "ขั้นตอนถัดไป" ไม่ใช่สรุป
   รายละเอียดเต็มใช้ `references/voice-th-b2b.md` ในสกิล `bsc-seo-article-writing` แล้วคัดลอกมาเป็น `content/articles/VOICE-GUIDE.md` ของโปรเจคนี้
4. **ข้อเท็จจริงทุกตัวต้องมาจากแหล่งของลูกค้า** (หน้าสินค้า สเปกชีท ผลทดสอบ หน้าบริการ) และระบุที่มาใน frontmatter
   สิ่งที่ไม่มี (ราคาจริง เลขกฎหมาย ชื่อวิศวกร ตัวเลขโครงการจริง) ให้ทำเป็นช่อง `___` พร้อมโน้ตว่าใครต้องเติม
   ห้ามเอาช่องว่างขึ้นเว็บจริง ประโยคเชิงเทคนิคที่ไม่ได้มาจากเว็บลูกค้าให้ลิสต์ไว้ในหัวข้อ "ต้องให้ลูกค้ายืนยันก่อนขึ้นเว็บ"
5. **ลิงก์ภายใน** ทุกบทมีลิงก์เข้าหน้าสินค้า/บริการอย่างน้อย 3 ลิงก์ (anchor เป็นชื่อสินค้าจริง) และลิงก์ไปบทความที่เกี่ยวข้อง
   เช็ค cannibalization กับบทเดิมก่อนเขียน แล้วบันทึกว่าบทเดิมบทไหนต้องแก้
6. **รูป**: ไม่ต้องหารูป เขียนสเปกให้ฉันเจน บทละ 4 รูป (ปก 1600×840, ในเนื้อหา 1200×675 ×2, og 1200×630)
   WebP ไม่เกิน 150 KB ชื่อไฟล์ภาษาอังกฤษ alt ภาษาไทยที่บรรยายสิ่งที่เห็นจริง ใส่สเปกใน frontmatter ของ .md
7. **Lint ก่อนส่งทุกบท**: `python3 ~/.claude/skills/bsc-seo-article-writing/scripts/lint_article.py content/articles/NN-slug.md`
   FAIL ต้องแก้ทุกจุด WARN อ่านแล้วตัดสินเอง
8. **Git**: commit หลังจบงานแต่ละชิ้น push ทันที บอกเลข commit ตอนรายงาน ไฟล์ที่ไม่ควรขึ้น git (โฟลเดอร์ใหญ่ ไฟล์ต้นฉบับ) ให้ถาม
9. **อย่า screenshot เพื่อตรวจ UI** ฉันดูในเบราว์เซอร์เอง เช็ค production ด้วย curl ครั้งเดียวพอ (ยิงถี่แล้วโดน 403)
10. **ก่อน `next build` เช็คว่า dev server ที่รันอยู่เป็นของโปรเจคนี้หรือเปล่า** (`lsof -iTCP:3000` แล้วดู title) build ทับ .next ของ dev ที่รันอยู่จะทำให้ hydration พังเงียบ
11. เวลาฉันบอกให้ "เปลี่ยนเรื่อง" บทไหน ให้เสนอตัวเลือก 3 เรื่องพร้อม keyword และเหตุผลสั้น ๆ แล้วรอฉันเลือก
    บทเก่าย้ายไป `content/articles/_archive/` ไม่ลบ อัปเดตแผน artifact และ Doc ให้ตรงด้วย
12. รายงานผลตามจริง อะไรยังไม่ได้ทำหรือติดอะไรให้บอกตรง ๆ ไม่ต้องขอโทษ

## เฟส 1: Research เว็บ + แผนงานเป็น checklist

```
จะทำ SEO ให้เว็บนี้ ช่วย research แบบละเอียด แล้วทำแผนงานเป็น checklist ที่ติ๊กได้

สิ่งที่ต้องตรวจจริง (จากโค้ดใน repo และจาก production ไม่ใช่เดา):
- สถานะ index: ค้นชื่อแบรนด์ใน Google ผลลัพธ์เป็น URL ใหม่หรือ URL เก่า, redirect จาก URL เก่าทำงานไหม (ทดสอบจริง)
- canonical ทุกหน้า, หน้าที่ canonical ชี้ออก, query string ที่สร้างเนื้อหาซ้ำ
- structured data (JSON-LD) มีอะไรบ้าง ขาดอะไร (Organization/LocalBusiness, Product, Service, Article, BreadcrumbList, FAQPage)
  หมายเหตุ: FAQPage ไม่ได้ rich result แล้วตั้งแต่ พ.ค. 2569 ใส่เป็นสัญญาณให้ AI search เท่านั้น
- Open Graph / twitter card (ลูกค้ากลุ่มนี้แชร์ลิงก์ผ่าน LINE)
- sitemap: มี URL ครบไหม lastmod เป็นวันจริงหรือเวลา build, robots.txt
- title/description ยาวเกิน 60 ตัวอักษรไหม ซ้ำกันไหม, h1 หน้าละหนึ่ง, ลำดับ h2/h3
- รูป: next/image หรือ srcset, lazy, ขนาดไฟล์ใหญ่สุด, alt ว่าง
- internal link: บทความ → หน้าสินค้า/บริการ กี่ลิงก์, หน้าสินค้า → บทความ กี่ลิงก์
- หน้า 404, error page, privacy policy (PDPA), breadcrumb ที่มองเห็น
- NAP: เบอร์โทร ที่อยู่ ตรงกันทุกหน้าไหม รวมข้อความ error ของฟอร์ม
- ความยาวและ metadata ของบทความเดิม (วันที่เป็นข้อความไทย ใช้กับ schema ไม่ได้)
- Core Web Vitals เบื้องต้น (TTFB, LCP element, CLS)

ผลลัพธ์ที่ต้องการ:
1. ปัญหาเรียงตามผลกระทบ P0 / P1 / P2 แต่ละข้อมีหลักฐานที่วัดได้ + วิธีแก้
2. รายการสิ่งที่ทำไว้ดีแล้ว ไม่ต้องแตะ
3. ตาราง keyword หลัก → หน้าเป้าหมาย (หนึ่งคำต่อหนึ่งหน้า) พร้อมประเภท (ซื้อ/บริการ/ความรู้/กฎหมาย)
   และคู่แข่งที่เจอบนหน้าแรกจากการค้นจริง ระบุว่าคำไหนชนะได้เร็ว (ชื่อสินค้า/แบรนด์) คำไหนต้องใช้เวลา
4. แผนบทความ 12 บท: ชื่อเรื่อง (ประโยคบอกเล่า keyword อยู่ต้น ≤60 ตัวอักษร), keyword หลัก, ประเภท,
   จำนวนคำเป้าหมาย, หน้าสินค้า/บริการที่จะลิงก์เข้า, จำนวนรูป
   บทต้องไม่ทับ intent กับบทเดิมในเว็บ ถ้าทับให้บอกว่าจะแบ่งหน้าที่ยังไง
5. Checklist งานทั้งหมดแบ่งเป็นเฟส (ตั้งระบบวัดผล → technical → schema/OG → on-page → internal link →
   บทความ → รูปและความเร็ว → local/off-page → วัดผล) ทำเป็น artifact ที่ติ๊กได้และบันทึกสถานะร่วมกันได้
   ใส่ตัวเลขว่ามีกี่ข้อ ใช้ตัวเลขจากที่ตรวจจริงเท่านั้น

ยังไม่ต้องแก้อะไรในเว็บ รอฉันดูแผนก่อน
```

## เฟส 2: Voice guide + บทแรกเพื่อปรับโทน

```
เห็นแผนแล้ว งานแก้เว็บเดี๋ยวค่อยทำ มาที่ keyword กับบทความก่อน

1. ไปอ่านสกิล bsc-seo-article-writing ให้ละเอียด (references/voice-th-b2b.md, seo-structure.md, sources.md)
   แล้วสร้าง content/articles/VOICE-GUIDE.md ของโปรเจคนี้ ปรับผู้อ่านและศัพท์เฉพาะทางให้ตรงลูกค้า
   รวมกฎ 10 ข้อ ตารางคำต้องห้าม รายการโครงสร้างที่ AI ชอบทำ และ checklist ก่อนส่ง
2. เก็บข้อเท็จจริงจากเว็บลูกค้าก่อนเขียน: ไล่อ่านหน้าสินค้า สเปก ผลทดสอบ หน้าบริการ หน้ามาตรฐาน หน้าเกี่ยวกับเรา
   จดตัวเลขที่ใช้ได้ทั้งหมด (ขนาดบรรจุ อัตราการใช้ ค่ามาตรฐาน ชื่อสถาบัน ปี เวลาแห้ง จำนวนโครงการ)
   และจดจุดที่เว็บลูกค้าขัดกันเอง (ตัวเลขไม่ตรงระหว่างหน้า) ไว้ถามลูกค้า
3. เขียนบทที่ 1 ตามแผน เป็นไฟล์ .md เท่านั้น ยังไม่ต้องขึ้นเว็บ ยังไม่ต้องทำ Doc
   ใช้ assets/article-template.md เป็นโครง frontmatter (SEO meta, keyword, แหล่งข้อเท็จจริง, การแบ่งหน้าที่กับบทเดิม,
   ลิงก์ภายใน, สเปกรูป 4 รูป, ต้องให้ลูกค้ายืนยันก่อนขึ้นเว็บ)
   ความยาว 1,500–2,000 คำ FAQ 4–6 ข้อจากคำถามที่ฝ่ายขายเจอจริง ปิดด้วย "ขั้นตอนถัดไป" ที่บอกว่าผู้อ่านต้องส่งอะไรมา
4. รัน lint จนไม่มี FAIL แล้วบอกฉันด้วยว่า WARN เหลืออะไรและทำไมถึงปล่อยไว้
5. รายงานสิ่งที่ต้องขอจากลูกค้าเพื่อให้บทนี้สมบูรณ์ (เช่น ตารางความหนา ชื่อวิศวกรและเลขทะเบียน ราคา กรณีศึกษาจริง)

ส่งบทที่ 1 มาให้ดูก่อน ฉันจะปรับ voice tone แล้วค่อยไปต่อ
```

หลังอ่านบทแรกแล้ว ใช้ข้อความนี้ต่อ:

```
ประเมินบทที่ 1 ตัวเองก่อน: เนื้อหาโอเคหรือยัง ต้องปรับตรงไหน อ่านยากไปไหม
ให้ดูเป็นตัวเลข: ความยาวประโยคแรก, จำนวน "จึง" "ซึ่ง" ต่อ 1,000 คำ, ย่อหน้าที่ไม่มีตัวเลข, ประโยคสรุปท้ายย่อหน้า,
ข้อเท็จจริงที่เล่าซ้ำสองที่, FAQ ที่ตอบซ้ำเนื้อหาในบท แล้วแก้ให้เลย
<ใส่ความเห็นของฉันเรื่องโทนตรงนี้ เช่น สุภาพขึ้น, ลดคำพูดปาก, สั้นลง>
แก้เสร็จแล้ว publish บทที่ 1 ขึ้นเว็บจริงตาม pattern ของบทเดิมในโปรเจค (รูปยังไม่ต้องใส่)
สร้างตัวแปลง .md → HTML ของเว็บ (โหมดปกติ) และ .md → HTML ธรรมดาสำหรับ Google Doc (โหมด --doc)
ไว้ที่ scripts/ ของเว็บ ใช้ scripts/md2article-example.py ในสกิลเป็นแบบ ปรับ inline style ให้ตรงบทเดิม
build ให้ผ่าน commit push แล้วเช็ค production ว่า title กับ h1 ขึ้นเวอร์ชันใหม่จริง
แล้วสร้าง Google Doc "1. <ชื่อเรื่อง>" ในโฟลเดอร์ Drive (เนื้อหา + คีย์เวิร์ดเท่านั้น)
```

## เฟส 3: บทที่ 2–12

```
ต่อไปเขียนบทที่ 2 ถึง 12 ตามแผน ทำแบบเดียวกับบทที่ 1 ทุกบท:
- .md ที่ content/articles/NN-slug.md ครบ frontmatter
- lint ผ่าน ไม่มี FAIL
- Google Doc "N. ชื่อเรื่อง" ในโฟลเดอร์ Drive เนื้อหา + คีย์เวิร์ดเท่านั้น
- ยังไม่ต้องขึ้นเว็บ รอลูกค้ารีวิวโทนและวิศวกร/ฝ่ายเทคนิคยืนยันตัวเลขก่อน
- บทที่เนื้อหาเป็นกฎหมาย/มาตรฐาน ให้ระบุเลขกฎหมายเฉพาะที่พบในเว็บลูกค้า ถ้าเว็บลูกค้าระบุขัดกันให้ยกทั้งสองแล้วโน้ตไว้
- บทกรณีศึกษาถ้าไม่มีข้อมูลโครงการจริง ให้บอกฉันก่อนเขียน อย่าทำเป็นโครงร่างที่มีช่องว่าง 60 ช่อง

ระหว่างเขียน ถ้าเจอว่าหัวข้อไหนในแผนไม่มีข้อเท็จจริงพอ หรือทับกับบทเดิม ให้เสนอเรื่องแทน 3 ตัวเลือกแล้วรอฉันเลือก
เสร็จแล้วอัปเดตแผน artifact (ตารางบทความ + checklist) ให้ตรง แล้วลิสต์ชื่อทั้ง 12 บทพร้อม keyword และสถานะ
สุดท้ายลิสต์รวมว่าต้องขออะไรจากลูกค้าบ้าง จัดกลุ่มตามบท
```

เมื่อจะเปลี่ยนหัวข้อหรือเปลี่ยนเรื่อง:

```
ข้อ <N> เปลี่ยนหัวข้อให้หน่อย            → เสนอ 3 ชื่อ (keyword อยู่ต้น ≤60 ตัวอักษร) รอเลือก แล้วแก้ .md, H1, Doc (ลบสร้างใหม่), artifact
ข้อ <N> เอาออก เปลี่ยนเป็นเรื่องอื่นเลย   → เสนอ 3 เรื่องที่ไม่ทับบทเดิม มีข้อเท็จจริงในเว็บลูกค้าพอ รอเลือก
                                          แล้วเขียนใหม่ทั้งบท ย้ายบทเก่าไป _archive อัปเดต Doc/artifact/หน้ารายงาน keyword
```

## เฟส 4: ขึ้นเว็บและเชื่อมลิงก์ (หลังลูกค้ารีวิวผ่าน)

```
ลูกค้ารีวิวผ่านบทที่ <รายการ> แล้ว ยืนยันตัวเลขที่ flag ไว้ดังนี้: <ใส่คำตอบของลูกค้า>
1. แก้ .md ตามที่ลูกค้ายืนยัน ลบช่อง ___ ให้หมด รัน lint ใหม่
2. แปลงขึ้นเว็บด้วยตัวแปลง ลงทะเบียนบทความในระบบของเว็บ (รายการบทความ, การ์ดหน้ารวม, related) ตาม pattern บทเดิม
3. ใส่รูปที่ฉันเจนไว้ที่ <path> ตามชื่อไฟล์ใน frontmatter พร้อม width/height และ alt
4. เชื่อมลิงก์กลับ: หน้าสินค้า/บริการที่บทลิงก์เข้า ให้เพิ่มลิงก์กลับมาบทความ 2–3 ลิงก์ และแก้บทเดิมที่ frontmatter บอกว่าต้องแก้เพื่อไม่ให้แย่ง keyword
5. build ผ่าน commit push เช็ค production ครั้งเดียว (title, h1, canonical, มีใน sitemap)
ทำทีละบท รายงานเลข commit ทุกบท
```

## เฟส 5: หน้ารายงานให้ลูกค้าดู

```
ทำหน้าแผนคีย์เวิร์ดให้ลูกค้าดูบนโดเมนของลูกค้าเอง ที่ /reports/seo-keywords
- เนื้อหา: หลักการเลือกคีย์เวิร์ด 3 ข้อ, ตาราง keyword หลัก → หน้าเป้าหมาย + ประเภท + คู่แข่ง, ตาราง keyword ของบทความ 12 บท (หลัก/รอง)
  ดึง keyword จาก frontmatter ของ .md ตรง ๆ ไม่พิมพ์ซ้ำ
- ไม่ใส่ปัญหาที่เจอ checklist สถานะภายใน หรือโน้ตถึงทีม
- noindex, nofollow ไม่อยู่ใน sitemap ไม่ผ่าน CMS ไม่ติดปุ่ม LINE/สคริปต์หน้าบ้าน
- โทนสว่างอย่างเดียว ใช้สีแบรนด์ลูกค้าและฟอนต์ที่ layout โหลดอยู่แล้ว
- build ผ่าน commit push แล้ว curl production ครั้งเดียวเพื่อยืนยัน 200 + meta robots
ถ้ามี artifact แผนภายในอยู่แล้ว ให้แยกหน้านี้ออกมาเป็นอีกไฟล์ ไม่แตะแผนภายใน
```

## บทเรียนจาก Infinite ที่ควรบอก Claude ล่วงหน้า

- Doc รอบแรกติด SEO meta กับสเปกรูปไปทั้งชุด ต้องลบสร้างใหม่ทั้งหมด ให้กำหนดขอบเขต Doc ตั้งแต่ข้อความแรก (กฎข้อ 2)
- ฉันอาจย้ายไฟล์ใน Drive ไปโฟลเดอร์ย่อยหรือลบ Doc เก่าเองระหว่างทาง Claude ต้อง list โฟลเดอร์ก่อนสร้างทุกครั้ง ไม่ใช้ id ที่จำไว้
- artifact ที่สร้างไว้ในเซสชันก่อนหายจาก scratchpad ให้ `action: read` ด้วย url แล้วแก้บนเวอร์ชันนั้น ไม่สร้างใหม่
- port 3000 ในเครื่องอาจเป็น dev server ของโปรเจคอื่น เช็ค title ก่อนเชื่อผล curl localhost
- บทกรณีศึกษาที่ไม่มีข้อมูลจริงกลายเป็นโครงร่าง 66 ช่องว่างที่ใช้ไม่ได้ ถ้าไม่มีข้อมูลให้เปลี่ยนเรื่องตั้งแต่ตอนวางแผน
- บทที่เป็นสินค้ารอง (ซีเมนต์กันไฟ, สีสะท้อนความร้อน) ถูกเปลี่ยนออกทั้งหมด แผน 12 บทควรเน้นสินค้าหลักและงานบริการที่มีมูลค่าสูงตั้งแต่แรก
- ตัวแปลง .md → HTML โหมด --doc เขียนไว้แต่ลืม commit ไปหลายชั่วโมง หลังสร้างสคริปต์ให้ commit ทันที
- ลูกค้าอาจแก้ใน Google Doc โดยตรง (modifiedTime เปลี่ยน) ต้องถามว่าแก้ตรงไหนแล้วเอากลับมาใส่ .md ไม่งั้นเว็บได้เวอร์ชันเก่า
- ราคาจริงไม่มีในเว็บ บทเรื่องราคาให้ใช้คอลัมน์ "วิธีคิดราคา" แทนตัวเลข ห้ามแต่งราคา
- เลขกฎกระทรวงในเว็บลูกค้าขัดกันเองระหว่างหน้า (ฉบับที่ 48/60 กับ ฉบับปี 2566) ให้ยกตามหน้าที่อ้างอิงและ flag ไม่เลือกเอง
